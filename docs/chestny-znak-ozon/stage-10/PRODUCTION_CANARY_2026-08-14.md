# Production canary ввода в оборот 14 августа 2026 года

Статус: завершён как инцидент; успешный end-to-end canary не подтверждён.

## Объект

- Ozon FBS posting: `0141094663-0075-1`;
- SKU: `D16-TSH-PRT-WGRY-XL`;
- GTIN: `04628837736914`;
- безопасный fingerprint КМ: `919a6fa790f8`.

Полный КМ, подпись и payload в документ не включены.

## Фактическая последовательность

1. КМ был получен из СУЗ, импортирован в зашифрованный пул, назначен одной
   физической единице, напечатан и физически нанесён.
2. Админка сформировала и подписала `LP_INTRODUCE_GOODS` реальной УКЭП.
3. Create endpoint вернул успешный HTTP-ответ в неожиданном текстовом формате,
   поэтому локальный документ перешёл в `crpt_submit_outcome_unknown`.
4. В ЛК ГИС МТ найден созданный документ. Он обработан с ошибкой: не указан
   вид документа, подтверждающего соответствие.
5. До завершения сверки товар был физически передан Ozon. Актуальный Ozon
   status стал `delivering / posting_on_way_to_city`; exemplar КМ отсутствует.
6. Штатная синхронизация обновила локальный заказ. По подтверждению владельца
   внутренний handover записан в `observe`-режиме: готовый товар списан,
   marking unit имеет custody `ozon`, создан manual-review процесс.

## Что не выполнялось

- повторный `LP_INTRODUCE_GOODS`;
- передача КМ в Ozon;
- дистанционный вывод из оборота;
- автоматический `LP_RETURN` или иная компенсирующая операция.

КМ не получил подтверждённый `in_circulation`, поэтому автоматический вывод из
оборота для него недопустим. Дальнейшее решение по уже переданной физической
единице остаётся ручным compliance-инцидентом; система не должна угадывать его.

## Исправления после canary

Миграция `0021_marking_crpt_conformity_reconciliation.sql` и связанный release:

- хранят проверенные вид, номер и дату РД на trade item;
- добавляют `certificate_document_data` в payload True API;
- блокируют ввод до внешней записи, если действующего РД нет;
- принимают строго валидный plain-text document ID от create endpoint;
- сверяют неоднозначный create по типу, группе, ИНН и hash исходного content;
- не ослабляют подготовительные этапы заказа, печати и нанесения КМ;
- оставляют все внешние write flags выключенными.

Дополнительная миграция `0022_marking_reconciliation_worker_acl.sql` устраняет
ошибку первого web-вызова сверки: админка теперь только ставит read-only
  reconciliation в durable queue, а True API, signer и привязка результата
выполняются изолированной ролью `getomerch_marking_worker`. Веб-роль
`getomerch_app` лишена права прямой привязки внешнего документа.
Фактический status-ответ True API возвращает товарную группу `LP` и не содержит
необязательный `senderInn`; проверка нормализует регистр группы, проверяет ИНН
при наличии поля и всегда требует точного совпадения hash удалённого content с
ранее подписанным локальным payload.

Сверка завершилась статусом `rejected` и привязала внешний ID только после
успешной проверки content. Причина отклонения: отсутствует вид документа,
подтверждающего соответствие. Ошибка True API содержала идентификационную часть
КМ; redaction и миграция `0023_marking_error_message_redaction.sql` закрывают
этот класс утечки в UI, safe views, jobs и сохранённых сообщениях.

## Следующий canary

менять: `LP_INTRODUCE_GOODS -> in_circulation -> Ozon set/status -> handover`.
