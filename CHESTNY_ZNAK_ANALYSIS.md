# Честный Знак × GetoMerch — анализ и план автоматизации

Документ-анализ: как встроить работу с маркировкой «Честный Знак» (ГИС МТ)
в GetoMerch, чтобы максимально убрать ручную рутину. Покрывает: нормативный
контекст, обзор API Честного Знака и Ozon Seller API по маркировке, целевые
сценарии автоматизации, доработки БД/админки и поэтапный roadmap.

Дата анализа: июль 2026. Перед реализацией сверить актуальные версии методов
в документации (Ozon: https://docs.ozon.ru/api/seller/, ЧЗ: ЛК ГИС МТ →
«Помощь» → документация True API / СУЗ).

---

## 1. Почему это касается нас (нормативный контекст)

Наш ассортимент — футболки, худи, свитшоты. Всё это **обязательная маркировка
«лёгкая промышленность» (товарная группа `lp`)**:

- Худи/свитшоты (трикотажные джемперы, ТН ВЭД 6110) — маркируются со
  «второй волны» легпрома (с 01.04.2024).
- Футболки/майки (ТН ВЭД 6109) — с «третьей волны» (с 01.03.2025).
- С 01.01.2026 продажа немаркированных остатков запрещена; остатки нужно
  было описать, заказать КМ и ввести в оборот до 01.03.2026.
- Маркетплейсы работают в «разрешительном режиме»: Ozon сверяет коды с ГИС МТ
  и не пропускает товар с невалидным/чужим/не введённым в оборот кодом.
  С 01.10.2026 обязательная проверка разрешительной документации селлера
  площадкой ужесточается.

**Важно про нашу роль.** Мы не просто продавец — мы *производитель*:
покупаем заготовки (немаркированный «сырьевой» товар в нашей модели учёта),
наносим принт/вышивку → получаем готовое изделие. Юридически готовое изделие
вводим в оборот мы. Значит, нам нужен полный цикл: описание товара → заказ
кодов → нанесение → ввод в оборот → передача кодов Ozon при отгрузке →
вывод из оборота.

Зоны ответственности по схемам Ozon:

| Схема | Передача кодов Ozon | Вывод из оборота |
|---|---|---|
| FBO | УПД с кодами через ЭДО при поставке на склад Ozon | Ozon выводит сам при продаже |
| FBS | Код каждого экземпляра при сборке отправления (API/ЛК) | По текущим правилам — зона продавца (документ «вывод из оборота, дистанционная продажа»); на практике Ozon постепенно забирает это на себя — **сверить актуальное состояние в ЛК Ozon перед реализацией этапа 4** |

Штрафные риски: продажа без КМ / с невалидным КМ — административка
(до конфискации), плюс блокировки карточек и отклонение отгрузок Ozon.

## 2. Экосистема API Честного Знака

Всё крутится вокруг четырёх контуров (у всех единая авторизация True API):

### 2.1. True API (ГИС МТ) — ядро

- База: `https://markirovka.crpt.ru/api/v3/true-api` (есть песочница
  `markirovka.sandbox.crptech.ru` — выдаётся по заявке).
- **Авторизация — самое неприятное место**: `GET /auth/key` возвращает
  `{uuid, data}`; строку `data` нужно подписать **УКЭП (ГОСТ Р 34.10-2012,
  открепленная подпись CMS/PKCS#7, base64)** и отправить в
  `POST /auth/simpleSignIn` → JWT-токен на **10 часов**. Т.е. без
  криптографии (КриптоПро CSP + сертификат ИП) токен не получить —
  см. раздел 5 про архитектуру «подписанта».
- Ключевые возможности:
  - `GET /cises/info`, `POST /cises/info` — статус кодов (EMITTED →
    APPLIED → INTRODUCED → RETIRED), владелец, GTIN;
  - `POST /lk/documents/create` — подача документов: **ввод в оборот**
    (`LP_INTRODUCE_GOODS` — производство РФ), **вывод из оборота**
    (дистанционная продажа), списание, перемаркировка;
  - `GET /lk/documents/list` — статусы обработки документов;
  - методы разрешительного режима (проверка кодов перед продажей).
- Документы на подачу тоже подписываются УКЭП.

### 2.2. СУЗ (Станция управления заказами) — заказ кодов

- Отдельный REST API (`/api/v2/lp/...`), идентификация по `omsId` +
  токен + подписанный УКЭП бизнес-заказ.
- Флоу: создать заказ КМ (GTIN + количество + способ выпуска) → дождаться
  статуса READY → забрать коды (`/codes`) блоками → коды в статусе EMITTED.
- Стоимость кода: 50 коп. без НДС (60 коп. с НДС) за штуку, списывается с
  лицевого счёта ЧЗ — счёт нужно пополнять (можно мониторить баланс по API).
- Полученные коды **нигде больше не скачать повторно спустя время** — их
  надо сразу сохранять у себя (наша таблица-пул, см. раздел 4.1).

### 2.3. Национальный каталог (НК) — карточки и GTIN

- Карточка товара в НК = обязательное описание (вид изделия, состав, размер,
  цвет, пол, возрастная группа) → получение/привязка **GTIN**. GTIN можно
  сгенерировать прямо в НК (или через членство в ГС1 РУС).
- API v3 (документация: https://docs.crpt.ru/gismt/API_НК/):
  - авторизация — `apikey` из ЛК Нацкаталога (или Bearer-токен True API);
  - `POST /v3/feed` — создание/обновление карточек пачкой (JSON или XML,
    лимит 25 МБ на фид) → возвращает `feed_id`;
  - `GET /v3/feed-status?feed_id=` — статус обработки, ошибки модерации;
  - выгрузка своих карточек/GTIN, справочники допустимых значений атрибутов;
  - **подписание карточек УКЭП** — черновик карточки становится
    «Опубликована» только после подписи (тоже есть методы в API).
- Для нас: **каждый SKU-вариант (модель × цвет × размер) = отдельный GTIN**.
  Каталог GetoMerch уже строит SKU ровно из этих атрибутов — карточки НК
  генерируются из нашей БД автоматически (см. раздел 4.5).

### 2.4. ЭДО Лайт — УПД для FBO

- Бесплатный ЭДО внутри ЧЗ с API. Поставка FBO требует УПД с перечнем кодов
  (или агрегатов) — Ozon принимает через своего оператора ЭДО с роумингом.
- Это самый бюрократический кусок; автоматизировать имеет смысл в последнюю
  очередь (у нас FBO — вторичная схема, см. приоритеты).

## 3. Маркировка в Ozon Seller API (актуальные методы, январь 2026)

Ozon два раза в 2025–2026 менял методы. Актуальный набор (старые
`/v4|v5/...exemplar/set` и пр. **удалены 13.01.2026**):

| Метод | Назначение |
|---|---|
| `POST /v3/posting/fbs/unfulfilled/list` | Уже используем. В ответе у постинга есть `requirements.products_requiring_mandatory_mark` — список SKU, для которых обязательна передача КМ |
| `POST /v6/fbs/posting/product/exemplar/create-or-get` | Получить/создать структуру «экземпляров» по отправлению (сколько единиц → столько экземпляров) |
| `POST /v6/fbs/posting/product/exemplar/set` | Передать по каждому экземпляру `mandatory_mark` (КМ DataMatrix), ГТД/РНПТ при необходимости |
| `POST /v5/fbs/posting/product/exemplar/validate` | Предварительная валидация кодов до сборки |
| `POST /v5/fbs/posting/product/exemplar/status` | Статус асинхронной проверки кодов Ozon-ом в ЧЗ (разрешительный режим) |
| `POST /v1/fbs/posting/product/exemplar/update` | Заменить код до передачи в доставку (если наклеили другой) |
| `POST /v4/posting/fbs/ship` | Сборка отправления — после успешного `exemplar/set` |

Целевой автоматический флоу FBS-отправления с маркированным товаром:

```
unfulfilled/list (requirements) → create-or-get → set(КМ) → validate →
ship → exemplar/status (дождаться passed) → package-label (печать)
```

Ozon сам сверяет переданные коды с ГИС МТ; невалидный код = блок отгрузки.
Поэтому пул кодов у нас должен хранить только реально введённые в оборот КМ,
а перед передачей полезно дополнительно бить `cises/info` (этап 3).

## 4. Что строим в GetoMerch

### 4.1. Модель данных (новые таблицы)

```
merch_products
  + gtin text UNIQUE          -- GTIN карточки НК (nullable, пока не описан)

merch_marking_codes           -- ПУЛ КОДОВ, центральная таблица
  id uuid PK
  cis text UNIQUE             -- полный КМ (GTIN+serial+крипточасть) — как отсканирован
  gtin text
  product_id uuid FK → merch_products (SET NULL)
  status text                 -- ordered|emitted|printed|applied|introduced|
                              --   assigned|shipped|retired|written_off
  suz_order_id text           -- заказ СУЗ, из которого получен
  posting_number text         -- какому отправлению Ozon передан
  introduced_doc_id text      -- документ ввода в оборот
  retired_doc_id text         -- документ вывода
  applied_at / introduced_at / shipped_at / retired_at timestamptz
  chz_status text             -- последний статус из cises/info (сверка)
  chz_synced_at timestamptz
  raw jsonb

merch_chz_code_orders         -- заказы КМ в СУЗ
  id uuid PK, suz_order_id text, gtin text, product_id FK,
  quantity int, status text, cost numeric, created_at, ready_at

merch_chz_documents           -- журнал документов ГИС МТ
  id uuid PK, doc_id text, type text (introduce|retire|writeoff|...),
  status text, payload jsonb, error text, created_at, processed_at

merch_chz_tokens              -- кэш токенов True API/СУЗ (см. раздел 5)
  id, kind text (true_api|suz), token text, expires_at
```

Правила в духе существующих инвариантов:

- Пул кодов — append-only по `cis`; статусная машина только вперёд
  (`emitted → applied → introduced → assigned → shipped → retired`),
  откаты — отдельными корректирующими событиями, как `merch_transactions`.
- `merch_marking_codes.product_id` — то, на что код *нанесён*. До нанесения
  код принадлежит GTIN (одному размеро-цвету), т.е. фактически SKU известен
  сразу — расхождение GTIN↔product ловим валидацией.
- Один КМ = один экземпляр = одна единица `quantity` в отгрузке.

### 4.2. Серверные роуты (по аналогии с `/api/ozon/*`)

```
src/app/api/chz/
  token/route.ts            -- получить/обновить токен (через подписанта)
  order-codes/route.ts      -- POST: заказ КМ в СУЗ по product_id/gtin+qty
  fetch-codes/route.ts      -- POST: забрать готовые коды заказа → в пул
  introduce/route.ts        -- POST: ввод в оборот (список cis)
  retire/route.ts           -- POST: вывод из оборота (дистанционная продажа)
  sync-status/route.ts      -- POST: cises/info по пулу → обновить статусы
  labels/route.ts           -- POST: PDF с DataMatrix-этикетками
src/app/api/ozon/
  exemplar/route.ts         -- POST: create-or-get + set + validate + status
```

Ключи/секреты ЧЗ — только на сервере, как с Ozon.

### 4.3. Новая страница `/marking` (админка)

- **Дашборд пула кодов**: матрица по SKU (в стиле `/inventory`) — свободных
  введённых в оборот кодов / нанесённых / переданных Ozon / выведенных.
  Индикатор «дефицита кодов»: свободных КМ меньше, чем остаток готовых
  изделий или чем открытых FBS-заказов → красный бейдж.
- **Заказ кодов**: диалог «выбрал SKU (или bulk по матрице) → количество →
  заказать» → фоново ждём готовности → коды падают в пул. Показ баланса
  лицевого счёта ЧЗ и стоимости заказа.
- **Печать этикеток**: выбрать свободные коды → PDF 58×40 (или наш формат)
  с DataMatrix + название/размер. После печати статус `printed`.
- **Журнал документов ЧЗ** (`merch_chz_documents`): как `/transactions`,
  со статусами обработки и ошибками.
- **Сверка**: кнопка «Сверить с ЧЗ» → `cises/info` по всем не-терминальным
  кодам, подсветка расхождений (у нас `introduced`, в ЧЗ `retired` и т.п.).

### 4.4. Встраивание в существующие флоу

**Производство (`api.produce`, ProduceDialog, цех):**
- При производстве печатной футболки/вышивки предлагаем привязать КМ:
  выбор свободного кода нужного GTIN из пула (или сканер — поле ввода,
  сканер работает как клавиатура). Код переходит в `applied`.
- Кнопка/автодействие «Ввести в оборот» — батчем по нанесённым кодам
  создаётся `LP_INTRODUCE_GOODS`. Вариант: авто-ввод сразу после производства
  (настройка-флажок в `/settings`).

**Заказы Ozon (`/orders`):**
- В карточке FBS-заказа блок «Маркировка»: сколько экземпляров требуют КМ
  (из `requirements`), какие коды назначены. Назначение — автоматом из пула
  (FIFO по introduced-кодам нужного GTIN) с возможностью пересканировать
  вручную фактически наклеенный код (это важно: Ozon получает код конкретного
  экземпляра, который физически поедет).
- Кнопки «Отправил заказ» / «Произвёл и отправил» расширяются: перед
  локальным списанием выполняют `exemplar/set → validate → ship`, помечают
  коды `shipped`, пишут `posting_number` в `merch_marking_codes`.
- **Кнопка «Скачать код»** в карточке заказа: по назначенным заказу КМ
  генерируется PDF-этикетка (DataMatrix + артикул/размер + человекочитаемый
  код) — распечатать и наклеить на товар перед отправкой. Технически:
  рендер GS1 DataMatrix из полного КМ (важно сохранить символы-разделители
  GS/ASCII 29 из крипточасти — иначе код не считается) через `bwip-js`,
  PDF через `pdf-lib`, формат под термопринтер (58×40) и под обычный A4
  (сетка этикеток). Скачивается тот же код, который передан/будет передан
  Ozon через `exemplar/set` — расхождение физической этикетки и данных
  исключено by design.
- Индикатор наличия (правило 9a) дополняется третьим ресурсом: **готовое +
  пустое + принт + свободный КМ**. Нет кода — заказ «не готов», даже если
  товар есть.
- После доставки (статус `delivered` из sync-orders) — фоновая подача
  «вывода из оборота, дистанционная продажа» по кодам заказа (этап 4;
  если выяснится, что Ozon уже выводит сам — просто сверяем статус).

**Каталог (`/products`):**
- Колонка GTIN + бейдж «нет карточки НК».
- Кнопка «Создать карточки в НК» — см. раздел 4.5.

### 4.5. Массовое создание карточек в Нацкаталоге

Исходное состояние: регистрация в НК есть, часть товаров не описана.
Цель: карточки на весь каталог создаются и досоздаются из GetoMerch, руками
в ЛК НК не заходим.

Маппинг атрибутов (наша БД → НК):

| GetoMerch | Атрибут НК | Откуда берём |
|---|---|---|
| `merch_product_categories` | Вид изделия + код ТН ВЭД (футболка → 6109, худи/свитшот → 6110) | новое поле `tnved`/`nk_kind` в справочнике категорий |
| `merch_fabric_types` | Состав сырья (%, например «хлопок 100%» / «хлопок 80%, полиэстер 20%») | новое поле `composition` в справочнике тканей |
| `merch_colors` | Цвет (из справочника допустимых значений НК) | новое поле `nk_color` (маппинг наших названий на словарь НК) |
| `merch_sizes` | Размер (рост/обхваты по требованию ТГ легпром) | новое поле `nk_size` |
| константы | Пол (унисекс), возрастная группа (взрослая), страна производства (РФ), товарный знак | блок «Честный Знак» в `/settings` |
| `merch_products.sku` | Артикул производителя | уже есть |
| — | Номер декларации/сертификата соответствия (ТР ТС 017/2011) | поле в `/settings` (на категорию); **без действующей декларации карточку не опубликовать — проверить, что она есть** |

Флоу автоматизации:

1. Страница `/marking` (или `/products`) → вкладка «Нацкаталог»: таблица
   SKU с признаком «есть GTIN / черновик / нет карточки». Сравнение —
   выгрузкой наших карточек из НК по API (сопоставление по артикулу).
2. «Создать недостающие» → собираем фид `POST /v3/feed` (запрашиваем
   генерацию GTIN в НК для новых), сохраняем `feed_id` в журнал
   (`merch_chz_documents`), поллим `feed-status`.
3. Ошибки модерации показываем в журнале построчно (как в Ozon import
   preview/apply — паттерн в проекте уже есть).
4. Успешные карточки подписываем УКЭП через API (на нашем сервере это
   просто, см. раздел 5), записываем GTIN в `merch_products.gtin`.
5. Хук на создание нового SKU: `findOrCreateProduct` помечает товар
   «нет карточки НК» → фоновая задача или ручная кнопка досоздания.

Один раз придётся разово заполнить маппинг-поля справочников (категорий,
тканей, цветов, размеров) — дальше новые SKU описываются сами.

**Дашборд (`/`):**
- KPI-карточка «Маркировка»: свободных кодов, ждут ввода в оборот,
  расхождения сверки, баланс лицевого счёта.
- Расходы на КМ (60 коп × заказано) можно автоматом писать в
  `merch_expenses` отдельной категорией.

## 5. Архитектура: свой сервер + УКЭП

True API и СУЗ требуют подпись ГОСТ-криптографией (КриптоПро CSP +
сертификат). Ozon-часть (раздел 3) криптографии не требует — только
Client-Id/Api-Key.

**Решение принято: GetoMerch переезжает на собственный сервер, УКЭП есть
(файловый контейнер на флешке).** Это снимает главное ограничение — подпись
живёт на том же хосте, что и приложение, отдельный «подписант»-микросервис
не нужен. Целевая схема:

```
Свой сервер (Linux):
  Next.js (GetoMerch, node/pm2 или Docker)
  КриптоПро CSP 5.0 для Linux + сертификат УКЭП
  signer-helper: маленький модуль (CLI-обёртка) — detached CMS-подпись
  cron: обновление токена True API/СУЗ каждые ~8 часов → merch_chz_tokens
Supabase — остаётся облачным (менять ничего не нужно)
```

Что нужно сделать на сервере:

1. **КриптоПро CSP 5.0 для Linux** — поставить, активировать лицензию
   (лицензия платная: годовая или бессрочная на один сервер, ~2–4 тыс. ₽;
   без лицензии работает 90 дней триала — хватит на обкатку).
2. **Перенести контейнер УКЭП с флешки** в локальное хранилище HDIMAGE
   (`csptest -keycopy` / штатная утилита) — чтобы флешку не держать
   воткнутой. Проверить, что контейнер экспортируемый; если ключ выпущен
   как неизвлекаемый (например, на Рутокене) — сервер должен видеть токен
   физически, либо перевыпустить УКЭП с файловым контейнером.
   ⚠️ УКЭП ИП из ФНС формально привязана к правилам хранения — копию
   защищаем правами доступа, наружу сервер не светим.
3. **Подпись из Node**: проще всего дергать CLI (`cryptcp -signf -detached`
   или `csptest`) через `child_process` — обёртка в `src/lib/chz/signer.ts`.
   Альтернатива — `cades` (КриптоПро ЭЦП SDK), но CLI надёжнее и проще
   в сопровождении.
4. **Токены**: cron-задача (или Route Handler + системный cron через curl)
   раз в 8 часов: `GET /auth/key` → подпись `data` → `POST /auth/simpleSignIn`
   → токен в `merch_chz_tokens`. Все ЧЗ-роуты берут живой токен из таблицы
   и умеют форсировать обновление при 401.
5. **Деплой**: `next build && next start` под pm2 (или Docker), reverse-proxy
   nginx + TLS, доступ к админке закрыть (basic auth / VPN / IP-allowlist —
   auth в приложении нет, RLS открытый, см. ARCHITECTURE.md).

Запасной вариант (если со своим сервером что-то не срастётся) — готовые
сервисы-посредники (SelSup, GetMark, Контур.Маркировка), но это абонентка
и двойной учёт; при нашей схеме они не нужны.

## 6. Roadmap

Статус подготовки: ✅ УКЭП есть (флешка), ✅ регистрация в ЧЗ, ✅ регистрация
в НК (карточки — частично), ✅ свой сервер под деплой. Осталось из
«нулевого» этапа: декларация соответствия ТР ТС 017/2011 (проверить),
пополненный лицевой счёт ЧЗ, договор ЭДО (только для FBO, не срочно).

### Этап 0 — сервер и криптография (фундамент)
- Деплой GetoMerch на свой сервер (pm2/Docker + nginx + basic auth).
- КриптоПро CSP, перенос контейнера УКЭП с флешки, `signer.ts`-обёртка.
- Cron обновления токена True API/СУЗ → `merch_chz_tokens`.
- Смоук-тест: получить токен, дернуть `cises/info` по одному коду из ЛК.

### Этап 1 — Ozon exemplar flow (быстрая победа, работает и без этапа 0)
- Таблица `merch_marking_codes` + импорт кодов (скан/CSV из ЛК ЧЗ).
- `requirements` из unfulfilled/list → индикатор «нужен КМ» в `/orders`.
- `exemplar create-or-get/set/validate/status` внутри «Отправил заказ».
- Кнопка «Скачать код» в карточке заказа — PDF с DataMatrix-этикеткой
  назначенного кода для печати и наклейки (см. 4.4).
- Результат: сборка FBS-заказов с маркировкой в один клик из админки,
  коды ведутся в нашей БД, а не в тетрадке.

### Этап 2 — Нацкаталог: карточки на весь ассортимент
- Маппинг-поля в справочниках (ТН ВЭД, состав, цвет/размер НК) + блок
  ЧЗ-констант в `/settings` (бренд, декларация, страна, пол, возраст).
- Выгрузка существующих карточек из НК, сопоставление по артикулу,
  `merch_products.gtin`.
- «Создать недостающие» через `/v3/feed` + `feed-status` + подписание
  карточек; журнал ошибок модерации. Хук на новые SKU.

### Этап 3 — пул кодов: заказ, печать, ввод в оборот
- Заказ КМ в СУЗ из админки (по GTIN из этапа 2), авто-забор кодов в пул.
- Страница `/marking`: матрица пула, дефицит кодов, журнал документов.
- Печать DataMatrix-этикеток (PDF).
- Привязка КМ при производстве (`applied`) и авто-ввод в оборот
  (`LP_INTRODUCE_GOODS`).
- `sync-status` по `cises/info` — регулярная сверка пула.

### Этап 4 — закрытие контура
- Авто-вывод из оборота по доставленным FBS (или сверка, если выводит Ozon).
- УПД/ЭДО для FBO-поставок (полуавтомат: генерация файла УПД с кодами).
- Алерты: дефицит кодов, зависшие документы, расхождения сверки, низкий
  баланс лицевого счёта. Возвраты: возврат выкупленного товара → код
  «повторный ввод в оборот» (отдельный документ) — сначала руками, потом
  автоматизировать по частоте.

Трудоёмкость (грубо): этап 0 ≈ 2–3 дня, этап 1 ≈ 3–5 дней, этап 2 ≈ 4–6
дней (больше всего возни с маппингом атрибутов и модерацией), этап 3 ≈ 1
неделя, этап 4 — по мере надобности. Этапы 0/1 независимы — можно вести
параллельно.

## 7. Риски и грабли

- **Версии Ozon-методов**: exemplar-методы уже дважды деприкейтились —
  закладывать версию в один модуль-клиент, не размазывать по коду.
- **Коды нельзя терять**: полученные из СУЗ КМ сохранять в БД немедленно и
  транзакционно; печать — только из БД.
- **Физика ↔ учёт**: наклеен должен быть ровно тот код, который передан
  Ozon. Поэтому сканер-ввод при сборке обязателен как опция, «авто-FIFO» —
  только если этикетки клеятся в момент сборки.
- **10-часовой токен**: все ЧЗ-роуты должны уметь «токен протух → понятная
  ошибка в тосте», а не 500.
- **Лимиты True API**: у методов есть rate-limit'ы; sync-status батчить
  (cises/info принимает до ~1000 кодов за запрос POST-версией).
- **Песочница**: у ЧЗ есть sandbox — этапы 2–3 обкатывать там, у Ozon
  exemplar-методы тестировать на реальном дешёвом заказе (бета-режим
  сборки в ЛК позволяет проверить без API).
- **FBO**: не автоматизировать раньше времени — объёмы поставок FBO у нас
  эпизодические, ручной УПД в ЭДО Лайт приемлем.
